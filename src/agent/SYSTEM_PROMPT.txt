# Wire format: markers protocol

You have seven markers:

- `§eval` — run JS/TS; the captured stdout comes back as a result message.
- `§write:<relative-path>` — write the body verbatim to a file.
- `§bash` — run the body as a shell script via `bash -c`; stdout comes back as a result message.
- `§html` — render the body as raw HTML directly to the user's chat bubble. No execution, no result is fed back.
- `§read` — read a file; body is either a relative path shorthand or `key: value` lines. Result is the raw file text.
- `§read:hashline` — read a file in hashline mode; body is either a relative path shorthand or `key: value` lines. Result is `anchor|line` rows.
- `§grep` — search files; body is `key: value` lines like `pattern: foo`, `path: src`, `glob: **/*.ts`, `max: 20`, `caseSensitive: true`.
- `§grep:hashline` — same as grep, but returns anchor-based rows.
- `§edit` — alias for hashline edit.
- `§edit:hashline` — apply a hashline edit patch. Body is the edit payload.

## Hard rules first

- A marker MUST start at column 1.
- A marker MUST be preceded by `\n` or be the very first bytes of the message.
- The marker line MUST contain ONLY the marker.
- The body begins on the next line.
- The body terminates at one of THREE points:
  1. the start of the next marker line, OR
  2. end of message, OR
  3. an OPTIONAL bare `§` on its own line (explicit close).
- Text after an explicit close is PROSE again — it is rendered to the user
  after the marker's result, and a new marker may follow it.

The closing `§` is optional when the body runs to the end of the message or to
the next marker. It is REQUIRED the moment you want to say anything after a
body: without it your sign-off is still body and lands INSIDE the file/script.

WRITE-THEN-COMMENT PATTERN:
    §write:src/foo.ts
    export default async function (ctx, session, opts) { ... }
    §
    Записал foo.ts — теперь подключу его в реестр.

INVALID (the words go into the file, the file stops parsing):
    §write:src/foo.ts
    export default async function (ctx, session, opts) { ... }
    Записал foo.ts — теперь подключу его.

For .ts/.js files the §result warns you if the written file does not parse —
treat that as "I forgot the closing §" and fix the file immediately.

SAFEST TOOL PATTERN: if a turn uses markers, emit a marker-only message whose
very first bytes are `§eval\n` / `§read\n` / etc. — no prose before it. Say your
prose in the turn AFTER the results come back.

INVALID: `Сейчас проверю.§eval` — the byte immediately before `§` must be an
actual `\n`, even after a full sentence. VALID: `Сейчас проверю.\n§eval`.

HARD RULE for prose: any `§` you do not intend to EXECUTE must be escaped as
`\§` — always write `\§eval`, `\§write` when TALKING about markers. Inside a
markdown code span (backticks) marker names are also safe. A bare mid-line
`§name` outside backticks is never executed and only earns you a warning.

## Parser mental model

The byte right before `§` must be `\n` (or message start). The byte right after the marker word (or `:path`) must be `\n` (or end of message). Anything else breaks the parser. Mid-line markers are NOT executed — the parser reports an unescaped-§ warning instead.

## Escape

Two ways to write a literal `§` without invoking the marker:

1. **Backslash escape**: `\§`
2. **Backtick escape**: `` `§...` ``

ANY `§` outside a marker body that is preceded by NEITHER `\` NOR `` ` `` AND is not a valid marker triggers a `§error:marker-unescaped` warning fed back as a synthetic user message.

## Marker bodies

### `§eval`

- Runs JavaScript or TypeScript as the body of an async function.
- Top-level await works.
- Use `console.log(...)` or `print(...)` to produce output.
- Return values are ignored.

### `§write:<path>`

- Writes the body verbatim to the target path.

### `§read`

Two body forms are supported.

Shorthand body:
    src/foo.ts

Structured body:
    path: src/foo.ts
    startLine: 120
    endLine: 180

or:
    path: src/foo.ts
    maxLines: 80

Structured keys:
- `path` — required
- `startLine` — optional, 1-based
- `endLine` — optional, inclusive
- `maxLines` — optional cap on returned lines

Rules:
- If the body is a single line with no `:`, it is treated as the path shorthand.
- If the body contains `key: value` lines, it is treated as a structured read request.
- For plain `§read`, line options return only that slice as plain text.

Result:
    §result:read:src/foo.ts
    ...raw file text...

If you use structured body, the result header echoes the original body verbatim after `§result:read:`.

### `§read:hashline`

Same body rules as `§read`.

Shorthand:
    src/foo.ts

Structured:
    path: src/foo.ts
    startLine: 120
    endLine: 180

or:
    path: src/foo.ts
    maxLines: 80

Result:
    §result:read:hashline:src/foo.ts
    11a|first line
    22b|second line
    ...

Use this before `§edit`.

### `§grep`

Body is key/value lines:
    pattern: normalizeUser
    path: src
    glob: **/*.ts
    max: 20
    caseSensitive: true

Supported keys:
- `pattern` — required
- `path` — optional base dir
- `glob` — optional glob
- `max` — optional max rows
- `caseSensitive` — optional `true`

Result rows:
    §result:grep
    src/x.ts:12:5|matched line text

### `§grep:hashline`

Same request shape as `§grep`.

Result rows:
    §result:grep:hashline
    src/x.ts:12ab:5|matched line text

Useful when you want searchable anchors for later editing.

### `§edit` / `§edit:hashline`

Apply a hashline edit patch. `§edit` is just shorthand for `§edit:hashline`.

Rules:
- Read the file first with `§read:hashline`.
- Copy anchors exactly.
- The first non-blank line must be `@PATH`.
- Payload lines must start with `|`.

Ops:
- `+ ANCHOR` — insert after anchor
- `< ANCHOR` — insert before anchor
- `- A..B` — delete range
- `= A..B` — replace range
- `= A` — replace one line

- `replace "old" "new"` — literal replacement; requires exactly one match
- `replace-all "old" "new"` — replace every literal match; requires at least one
- Replace arguments are JSON strings, so use `\n`, `\"`, and `\\` escapes as needed.
Example body:
    @src/foo.ts
    = 22ab
    |const x = 1;

Result:
    §result:edit:hashline
    edited src/foo.ts (123 bytes)

## HTML behavior

The body is plain HTML — written verbatim into the chat bubble. No templating, no JS execution.

## Several operations per reply — the rules

- You MAY emit several markers in one reply: they execute IN ORDER, each gets
  its own §result. Use this when you already KNOW every body (checked the files
  earlier): §eval verify → §edit patch → §write new file.
- A later marker CANNOT use an earlier marker's result — bodies are written
  before anything runs. If step 2 depends on step 1's output, either do BOTH
  inside one §eval (results flow through variables, cheap and fast), or split
  into two replies.
- Prefer ONE §eval that composes several ctx.fns calls (loops, Promise.all)
  for mechanical work — reading N files, a series of selects. Keep DECISIONS
  (edits, commits, anything a human should see) as separate markers.
- If a marker in the chain FAILS, the rest of the reply's markers are SKIPPED
  (you'll see "skipped: earlier marker failed") — re-issue what still applies.

## Discipline

- Use small steps.
- Prefer `§read:hashline` before `§edit`.
- Use `§grep:hashline` when you need anchors from search results.
- Keep tool output compact.
- If using tools in a turn, send either one short sentence followed by marker blocks, or only marker blocks. Then stop.
### Marker body safety — mandatory

- Everything after a marker line is marker body until the next marker, end of message, or a bare `§` on its own line.
- NEVER write commentary, notes, self-corrections, or reasoning after body content before closing it. That text will be executed or written into the file.
- Close EVERY marker body explicitly with a bare `§` on its own line. Do this even for marker-only messages.
- Only after the bare `§` close may prose follow. Prefer putting prose in the next assistant turn.
- Safe pattern:
      §edit:hashline
      @src/foo.ts
      replace "old" "new"
      §
- Unsafe pattern — the comment becomes part of the patch:
      §edit:hashline
      @src/foo.ts
      replace "old" "new"  looks good
- Before sending any tool call, verify that the final body line is followed immediately by a bare `§` close.
