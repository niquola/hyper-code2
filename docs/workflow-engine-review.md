# Review: дизайн workflow engine (`docs/workflow-engine-design.md`)

Статус: независимое review, код и исходный дизайн не менялись.
Дата: по состоянию кода в `src/agent/*` (workerLoop, wakeAt/wakeIn, wakeUpWhen, pollWatches, deliverWatch, deliverWakes, steer), `src/cron/*`, `src/procs/db/*` и живой схемы Postgres.

Обозначения:

- **[Проверено]** — подтверждено чтением кода / схемы БД (без воспроизведения тестом, если не сказано иначе).
- **[Гипотеза]** — правдоподобный вывод, требует эксперимента или обсуждения.

## 1. Краткий вердикт

Дизайн концептуально верный: decider-агент, истина в Postgres, короткие эпизоды LLM, проверки как обычные функции, ANY-семантика ожиданий, отказ от собственного языка workflow. Разделы 6 («Гарантии и границы») и 8 («Минимальные проверки») честные и полезные.

Главная проблема не в идеях, а в том, что дизайн описывает `task_waits` как новую подсистему, тогда как в коде уже есть почти эквивалентная `agent_watches` + протокол пробуждения агента. Одновременно в существующем протоколе есть два дефекта, которые станут блокерами для workflow, если их не починить до реализации:

1. пробуждение, доставленное **во время запуска** агента, теряет расписание при успешном завершении запуска;
2. ожидание в состоянии `checking` **не восстанавливается** после падения процесса.

Оба дефекта касаются ровно тех сценариев, которые дизайн перечисляет в разделе 8 (пп. 1, 2, 4).

## 2. Что уже есть в коде (карта переиспользования)

| Дизайн | Существующий механизм | Статус |
|---|---|---|
| «Поставить агента на запуск» (5.3 шаг 5) | `UPDATE agents SET next_run_at = COALESCE(next_run_at, now)` + user-сообщение `message_type='wake_up'`, `excluded_from_cursor=true` (deliverWakes, deliverWatch, steer) | [Проверено] — это и есть «согласованный с очередью механизм» |
| Сериализованный координатор (5.4) | `claimOne`: атомарный `UPDATE … WHERE run_state='idle' … RETURNING`, один запуск на агента | [Проверено] — получается бесплатно |
| Lease запуска, fencing, recovery | `run_token`, `run_heartbeat_at` (30 с), `RUN_LEASE_MS` 10 мин, `recoverStaleRuns` с backoff и лимитом 3 | [Проверено] |
| `task_waits.check_fn/check_args` | `agent_watches.predicate='runtime.fn'`, `opts={name,args,callTimeoutMs}` | [Проверено] — контракт `{ready, result}` уже совпадает с `ReadinessResult` минус `reason/evidence` |
| `poll_interval_ms`, `next_check_at`, `deadline_at` | `interval_ms`, `next_check_at`, `timeout_at` | [Проверено] |
| `check_token`, `check_lease_until` | только `status='checking'`, **без** токена и срока | [Проверено] — см. дефект 3.2 |
| `event_topic`, `event_filter` | нет durable источника; `procs.events` — in-memory `Set` подписчиков | [Проверено] — дизайн это признаёт |
| Чистый таймер (`deadline_at` без check) | `agents.wake_at` (один на агента) или watch с любым предикатом и `timeout_at` | [Проверено] |
| Виртуальные часы (8.10) | `pollWatches`/`deliverWatches` принимают `opts.now`; `claimOne`/finalize используют `Date.now()` | [Проверено] — частично |
| Periodic function runner | `cron_tasks`/`cron_runs` (claim + run history одним statement, recovery `running→error` при старте) | [Проверено] — образец для `workflow_events` + lease |

Вывод: **`task_waits` в 80% дублирует `agent_watches`.** Открытое решение из раздела 9 («переиспользование текущих wake/watch механизмов вместо новой `task_waits`») стоит закрыть в пользу расширения `agent_watches` (см. раздел 5).

## 3. Проверенные проблемы

### 3.1 Пробуждение во время запуска теряет расписание — [Проверено чтением кода, не воспроизведено]

Цепочка в `src/agent/workerLoop.ts`:

- `claimOne` при захвате ставит `next_run_at = NULL`.
- `deliverWatch`/`deliverWakes` ставят `next_run_at = COALESCE(next_run_at, now)` и добавляют user-сообщение с `excluded_from_cursor=true`.
- Финализация успешного запуска вычисляет `next_run_at` так:
  `CASE WHEN (MAX(idx) FROM messages WHERE role='user' AND excluded_from_cursor=0) > consumedIdx THEN COALESCE(next_run_at, ts+100) ELSE NULL END`.

Сообщение `wake_up` исключено из курсора, поэтому не считается «новой работой», и `ELSE NULL` **стирает** `next_run_at`, выставленный доставкой. Сообщение остаётся в транскрипте, но запуска нет — агент проснётся только от следующего внешнего триггера.

Почему это критично именно для дизайна: раздел 5.1 предлагает «сразу после регистрации проверка назначается на ближайшее время» (`wakeUpWhen` уже делает `next_check_at = now`). То есть типичный сценарий «координатор внутри своего run регистрирует ожидание, факт уже есть, проверка срабатывает за секунды, run ещё не закончился» ведёт прямо в этот race. Это сценарий 8.2 («событие во время регистрации»).

Контраст: `steer.ts` добавляет `team_update` **без** `excluded_from_cursor` (вопреки `docs/team-delegation.md`), поэтому обновления команды считаются реальной работой и не теряются. Для `wake_up` такой защиты нет.

Замечание: если во время run случится ещё один вызов модели, `run.ts` перечитает транскрипт (`syncAgentState` перед каждым вызовом), и сообщение будет увидено. Потеря происходит, когда доставка попадает в последний вызов модели или в хвост финализации.

### 3.2 Состояние `checking` у watch не восстанавливается — [Проверено]

`pollWatches` переводит строку в `status='checking'` и запускает `deliverWatch` в фоне (`void …`). Если процесс упадёт между ними, строка останется `checking` навсегда: индекс и выборка due учитывают только `status='active'`, `recoverStaleRuns` трогает только `agents`, а при старте нет прохода, аналогичного `cron.recover`. Это ровно сценарий 8.4 («падение проверяющего worker-а»). Дизайн правильно вводит `check_token`/`check_lease_until`; их нужно добавить в `agent_watches`, а не в новую таблицу.

### 3.3 Нет транзакционного примитива в `procs.db` — [Проверено]

`procs.db.select/run/insert/exec` — отдельные statements без `BEGIN`; `pool.begin` используется только в `llm/getAnthropicOAuthToken.ts` через сырой `conn()`. Дизайн трижды опирается на «одну транзакцию» (создание задачи + ожидания + событие; переход в `ready`; завершение задачи + продолжение). До реализации нужен либо `procs.db.transaction({ fn })`, либо решение писать всё одним statement через CTE (как `deliverWakes`). Второе проще и уже соответствует стилю кода, но ограничивает сложность переходов.

### 3.4 Лимиты `wakeUpWhen` не рассчитаны на месяцы — [Проверено]

`timeoutMs` ограничен 30 сутками, `everyMs` — от 5 с до 24 ч. Дизайн явно говорит про workflow «месяцами». При переиспользовании `agent_watches` лимит нужно снять или сделать deadline опциональным (сейчас `timeout_at NOT NULL` по логике кода).

### 3.5 `runtime.fn` — не allowlist — [Проверено]

`watchPredicate` вызывает любую зарегистрированную `ctx.fns.*` функцию по имени. Дизайн говорит «имя разрешённой runtime-функции». Сейчас никакого списка нет; проверка может вызвать функцию с побочными эффектами (например, отправку письма). Для workflow-проверок нужен явный allowlist или соглашение об именовании (`*.check*`, `*.ready*`) с валидацией при регистрации.

### 3.6 Ошибка проверки: нет backoff и лимита — [Проверено]

При исключении в предикате watch возвращается в `active` с `next_check_at = now + interval_ms`, `attempts++`, без роста интервала и без порога, после которого будить агента. Дизайн хочет backoff и «когда агент должен просыпаться из-за длительных ошибок» (раздел 9) — это нужно добавить.

### 3.7 Watches и wake не отменяются при stop/archive/clear — [Проверено]

Ссылки на `agent_watches`/`wake_at` есть только в wake-функциях и `workerLoop`. `pollWatches` не фильтрует `archived_at`, поэтому watch заархивированного агента сработает, допишет сообщение и выставит `next_run_at`, а `claimOne` его никогда не подберёт. Для `workflow.cancel/paused` дизайн должен явно отменять ожидания; полагаться на автоматическое поведение нельзя.

### 3.8 Результат проверки попадает в транскрипт целиком — [Проверено]

`deliverWatch` вставляет `Result: <JSON до 16 КБ>` в user-сообщение. Дизайн правильно предлагает ссылки/свидетельства вместо blob; при переиспользовании доставки нужно переопределить тело сообщения (короткая причина + `task_id` + `wake_event_id`), а данные класть в `workflow_events.payload`.

### 3.9 Повтор при ошибке запуска перевыполняет инструменты — [Проверено]

При abort/ошибке финализация **не сдвигает** `last_processed_msg_idx`, и тот же пользовательский ввод обрабатывается снова. Значит координатор может второй раз вызвать «создать задачу с ожиданием». Уникальность `(workflow_id, key)` из дизайна — не опция, а обязательное требование; API создания задачи должно требовать `key` по умолчанию.

## 4. Гипотезы и риски

- **[Гипотеза] Отдельный lease задачи не нужен.** Раз координатор сериализован `claimOne`, «обработку» задачи можно фиксировать как `workflow_tasks.status='running'` + `owner_run_token = agents.run_token`; завершающий UPDATE фенсится проверкой, что токен всё ещё активен. Отдельные `claim_token/lease_until` появятся только если исполнителем задачи станет кто-то кроме координатора.
- **[Гипотеза] Workflow ↔ agent session: один долгоживущий агент на workflow.** `sleepIdle` компактит транскрипт агентов старше 15 мин с ≥20 сообщениями; для многомесячного координатора это нормально и даже желательно, если при каждом пробуждении он читает состояние из `workflows/workflow_tasks/workflow_events` через функцию, а не из памяти. Требование: prompt пробуждения должен содержать инструкцию «прочитай состояние через `workflow.state`», иначе после компакции агент будет гадать.
- **[Гипотеза] `event_topic` в MVP лишний.** Без durable inbox с курсором подписка на in-memory `procs.events` даёт только «ускорение» с потерями при рестарте. Опрос + deadline покрывают визовый и медицинский примеры. Ввести `event_topic` после появления хотя бы одного durable источника (gmail-курсор, telegram и т.п.).
- **[Гипотеза] `ready` + `deadline` одновременно.** В существующем `deliverWatch` timeout проверяется до вызова предиката, так что при одновременности побеждает timeout, а не условие. Для визового примера («письмо пришло в момент дедлайна») лучше наоборот: если срок истёк, но предикат `ready`, записать `condition`. Это дешёвая правка в момент адаптации.
- **[Гипотеза] Один watch на задачу в MVP.** ANY над несколькими ожиданиями требует «отменить остальных» в той же транзакции (см. 3.3). Если на старте ограничиться одним ожиданием (проверка + deadline в одной строке — как `agent_watches` уже делает), ANY реализуется тривиально, а составные условия остаются задачей функции.
- **[Гипотеза] Hot reload функции проверки.** Сейчас `watchPredicate` резолвит функцию по имени в момент вызова, т.е. уже «исполняется актуальная версия», как дизайн и предлагает для MVP. Для удалённой функции сработает ветка ошибки (3.6) до истечения `timeout_at` — без backoff это шум каждые `interval_ms`.
- **[Гипотеза] Виртуальные часы.** Параметр `now` есть у poll/deliver, но `claimOne`/finalize используют `Date.now()`. Для теста 8.10 достаточно гонять `pollWatches({ now })` и проверять состояние таблиц без запуска LLM; полный прогон через worker потребует инъекции часов в `workerLoop`.

## 5. Рекомендации по MVP (в порядке приоритета)

1. **Починить 3.1 до всего остального.** Варианты: (а) считать в finalize «работой» также `message_type IN ('wake_up','team_update')`; (б) хранить факт доставки в отдельном флаге `agents.wake_pending`, который finalize преобразует в `next_run_at`. Добавить тест «watch срабатывает, пока агент running; после успешного finalize `next_run_at IS NOT NULL`».
2. **Добавить lease к `agent_watches`**: `check_token`, `check_lease_until`; в `pollWatches` выбирать `status='active' OR (status='checking' AND check_lease_until < now)`; финализирующие UPDATE фенсить по токену. Это закрывает 3.2 и покрывает 8.4.
3. **Не создавать `task_waits`.** Добавить в `agent_watches` колонки `task_id` (nullable), `deliver_kind` (`wake_up` | `workflow_task`), опциональный `timeout_at`, снять 30-дневный лимит. Доставка для `workflow_task` переводит задачу `waiting→ready`, пишет `workflow_events` и ставит `next_run_at` — одним CTE-statement, чтобы не зависеть от 3.3.
4. **Схема MVP — три таблицы**: `workflows`, `workflow_tasks`, `workflow_events`. Без `event_topic/event_filter`, без `claim_token/lease_until` у задачи (см. гипотезу про lease). `key` обязателен при создании задачи из агента.
5. **API из четырёх функций**: `workflow.create`, `workflow.scheduleTask({ workflowId, key, title, instructions, check?: {fn,args,everyMs}, deadlineAt? })`, `workflow.readyTasks({ workflowId })`/`workflow.state`, `workflow.completeTask({ taskId, result, next?: {…} })` — последняя выполняет завершение и создание продолжения одним statement/транзакцией.
6. **Allowlist проверок**: регистрация принимает только функции из явного списка либо с JSDoc-тегом/суффиксом; в `watchPredicate` этот фильтр не нужен, он нужен в `workflow.scheduleTask`.
7. **Backoff и порог ошибок**: `next_check_at = now + min(interval * 2^attempts_failed, cap)`; после N подряд ошибок — будить координатора с причиной `check_failing`, не дожидаясь deadline.
8. **Отмена**: `workflow.cancel/pause` явно переводит связанные watches в `cancelled`; `pollWatches` фильтрует `archived_at IS NULL` через join на `agents`.
9. **Транзакции**: либо ввести `procs.db.transaction`, либо зафиксировать в архитектуре правило «переход состояния = один statement с CTE» и держать переходы простыми.
10. **В раздел 8 добавить**: «watch срабатывает во время того же run, в котором был зарегистрирован» и «проверка успешна и deadline истёк в один тик».

## 6. Что в дизайне стоит оставить как есть

- Gap как вычисление, а не строка таблицы; engine не знает предметной логики.
- `ready: true` = «пора продолжить», а не «цель достигнута».
- Односторонняя гарантия и честный отказ от exactly-once для внешних действий (совпадает с `docs/durable-runs.md`).
- `paused` как явный статус, обычный сон не меняет статус workflow.
- Append-only `workflow_events`, ссылки вместо blob.
- Отказ начинать с нового scheduler-а — подтверждается: и очередь агентов, и watches, и cron уже существуют.
