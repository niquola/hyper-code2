# Workflow engine: агент-координатор и durable ожидания

Статус: черновик для обсуждения. Реализация не начата.

## 1. Идея

Один агент координирует один workflow: хранит цель, принимает решения, выполняет действия или делегирует работу. Дойдя до точки ожидания, он создаёт задачу самому себе и освобождает runtime. Engine продолжает следить за условиями и сроками и возвращает управление агенту, когда появляется повод.

Workflow может жить месяцы; один запуск LLM — только короткий эпизод его исполнения. Цель, задачи, результаты и ожидания живут в Postgres, независимо от контекстного окна и памяти процесса.

Это SWF-подобное разделение ответственности, не реализация AWS API:

- агент — decider, решает, что делать дальше;
- engine — хранение, расписание, проверки и надёжное пробуждение;
- обычные функции, агенты и человек — исполнители действий.

В первой версии нет своего языка workflow, обязательного DAG или replay произвольного async-кода.

## 2. Примеры

### Виза

Цель: паспорт с визой на руках; завершение требует подтверждения, а не только уведомления о доставке.

1. Агент помогает подготовить документы и фиксирует результат отправки.
2. Создаёт себе задачу: «Разобрать ответ консульства; при отсутствии ответа через три дня оценить follow-up».
3. Условие проверяет наличие подходящего письма. Событие о новой почте ускоряет проверку; периодический опрос страхует пропущенные сигналы.
4. Письмо либо срок ожидания делает задачу готовой.
5. Агент получает причину и свидетельства, перечитывает текущие факты и решает следующий шаг.

Тайм-аут не означает автоматическую повторную отправку письма: это повод для решения. Отправка письма и другие чувствительные действия сохраняют действующие требования подтверждения пользователя.

### Лекарства и давление

По заданному пользователем расписанию агент или обычная функция обнаруживает отсутствие записи за нужный период и организует напоминание. Отправленное напоминание не считается приёмом лекарства или измерением. Подтверждение пользователя сохраняется как отдельный факт. Отсутствие ответа не означает пропуск лекарства.

## 3. Gaps остаются в коде

Gap — вычисление над актуальными фактами, а не строка отдельной таблицы. Бизнес-правила живут в обычных runtime-функциях.

В БД сохраняется принятое решение ждать: имя функции проверки, аргументы, режим опроса и срок. Engine не знает медицинской или визовой логики.

Предлагаемый контракт функции готовности:

```ts
type ReadinessResult = {
  ready: boolean;
  reason?: string;
  evidence?: Array<{ reference: string; summary?: string }>;
};
```

`ready: true` означает «пора продолжить задачу», а не обязательно «все gaps закрыты». Обнаружение нового gap тоже может быть поводом продолжить работу. Адаптация gap-функции к этому контракту явная; engine не выводит готовность из длины массива gaps.

Проверка только читает данные, ограничена по времени и безопасна для повторного вызова. В ожидании хранятся имя разрешённой runtime-функции и JSON-аргументы, не произвольный исполняемый код. В аргументах — ссылки на секреты, не сами секреты.

## 4. Схема данных — предложение

Используем существующую `agents`, не создаём вторую очередь запусков агентов. Новые таблицы ниже отвечают за предметное состояние workflow.

### `workflows`

| Поле | Назначение |
|---|---|
| `id` | Идентификатор workflow |
| `agent_id` | Ссылка на агента-координатора; один координатор на workflow |
| `title`, `goal` | Название и цель |
| `completion_criteria` | Как проверить достижение цели |
| `status` | `active / paused / completed / failed / cancelled` |
| `result` | Итог или ссылки на артефакты, JSONB |
| `created_at`, `updated_at`, `completed_at` | Время жизни |

`paused` — явная остановка пользователем или координатором. Обычный сон в ожидании не требует менять статус workflow: он остаётся `active`. Наличие готовых задач и ожиданий — вычисляемое состояние.

### `workflow_tasks`

| Поле | Назначение |
|---|---|
| `id`, `workflow_id` | Идентичность и принадлежность |
| `key` | Необязательный стабильный ключ для идемпотентного создания |
| `title`, `instructions` | Что сделать при получении управления |
| `status` | `waiting / ready / running / done / failed / cancelled` |
| `input`, `result` | Структурированные данные и ссылки, JSONB |
| `wake_event_id` | Событие, сделавшее задачу готовой |
| `attempt` | Номер попытки обработки задачи |
| `claim_token`, `lease_until` | Владение текущей попыткой, если требуется отдельный claim |
| `created_at`, `updated_at`, `completed_at` | Время жизни |

Уникальность `(workflow_id, key)` для непустого ключа предотвращает повторное создание одного логического задания при восстановлении агента.

Граница между lease задачи и существующим lease запуска агента требует проверки перед реализацией: нельзя вводить два независимых владельца одной работы. Предпочтительно связывать обработку задачи с токеном существующего запуска агента.

### `task_waits`

| Поле | Назначение |
|---|---|
| `id`, `task_id` | Идентичность ожидания |
| `status` | `active / satisfied / timed_out / cancelled` |
| `check_fn`, `check_args` | Имя функции готовности и JSONB-аргументы; могут отсутствовать для таймера |
| `event_topic`, `event_filter` | Необязательный источник ускоряющих сигналов |
| `poll_interval_ms`, `next_check_at` | Период и срок следующей проверки |
| `deadline_at` | Разбудить не позднее указанного срока |
| `check_token`, `check_lease_until` | Защита параллельных проверок и опоздавших результатов |
| `last_checked_at`, `last_error` | Диагностика |
| `created_at`, `resolved_at` | Время жизни |

У задачи может быть несколько ожиданий. В первой версии действует **ANY**: первое выполненное условие или истёкший срок делает задачу готовой, остальные ожидания отменяются. ALL можно выразить одной составной проверкой; отдельную механику ALL пока не вводим.

Ожидание обязано иметь путь к проверке или пробуждению: опрос, надёжный источник событий либо deadline. Чистый таймер имеет только `deadline_at`.

### `workflow_events`

| Поле | Назначение |
|---|---|
| `id`, `workflow_id`, `task_id`, `wait_id` | Идентичность и связи; последние две необязательны |
| `kind` | Например `task.created`, `wait.satisfied`, `wait.timed_out`, `task.completed` |
| `source`, `source_event_id` | Источник и ключ дедупликации входящего события |
| `payload` | Причина, свидетельства, результат или ссылки, JSONB |
| `occurred_at`, `recorded_at` | Когда произошло и когда записано |

История append-only; транскрипт агента не заменяет её. Крупные письма и документы остаются в своих хранилищах, в истории — ссылки и нужные для решения факты. Проекции состояния и события переходов записываются одной транзакцией.

Индексы: готовые задачи по workflow, активные ожидания по `next_check_at` и `deadline_at`, ожидания по topic, история по workflow и времени. Для входящих событий — уникальный ключ источника в явно определённой области дедупликации.

## 5. Жизненный цикл

### Создание задачи и ожиданий

Одна транзакция создаёт задачу в `waiting`, её ожидания и событие `task.created`. Агент может продолжать другую работу; он освобождает выполнение, когда готовой работы больше нет.

Уход в сон не должен затирать уже поставленный запуск. Регистрация ожиданий и протокол освобождения существующего agent lease должны быть согласованы с очередью `agents`.

Сразу после регистрации проверка назначается на ближайшее время. Это позволяет увидеть факт, появившийся до подписки. Если факт может исчезнуть или существует только как кратковременный сигнал, нужен durable inbox/источник с курсором: один polling этого не гарантирует.

### Проверка

Engine выбирает наступившее ожидание, атомарно получает lease и вызывает функцию вне транзакции БД. Результат применяется только при совпадении token и активном состоянии ожидания. Ошибка проверки не равна `ready` и не закрывает задачу: записываем диагностику, повторяем с backoff, продолжаем учитывать deadline.

Событие обычно не будит LLM напрямую: оно назначает проверку подходящих ожиданий. Проверка подтверждает, что событие действительно относится к задаче.

### Пробуждение

При `ready: true` или наступлении deadline одна транзакция:

1. блокирует задачу и проверяет, что она ещё `waiting`;
2. записывает событие с причиной `condition` или `timeout` и свидетельствами;
3. переводит задачу в `ready` и сохраняет `wake_event_id`;
4. завершает выигравшее ожидание и отменяет остальные;
5. ставит существующего агента на запуск через согласованный с очередью механизм.

После commit можно отправить недолговечный сигнал worker-у. Истина остаётся в БД; потеря сигнала только задерживает обработку до следующего прохода.

Одновременные условие и тайм-аут дают один переход в `ready`: выигрывает первая принятая транзакция. При пробуждении агент всё равно перечитывает текущие факты.

### Обработка

Агент получает готовые задачи, причины и свидетельства, принимает решения и сохраняет результаты. При необходимости создаёт следующую задачу с ожиданиями. Завершение текущей задачи и регистрация её продолжения должны быть атомарны.

Несколько готовых задач одного workflow обрабатываются сериализованным координатором. Длительные самостоятельные работы можно делегировать; их результаты становятся фактами для проверок.

## 6. Гарантии и границы

- После рестарта ожидания и готовые задачи сохраняются.
- Доставка работы — с возможностью повторной обработки, не обещание exactly-once внешних действий.
- Переход одной задачи из `waiting` в `ready` принимается один раз; повторный сигнал его не дублирует.
- Устаревший исполнитель не может записать результат поверх новой попытки: token проверяется в завершающем UPDATE.
- Отправленное письмо могло уйти до падения процесса, даже если результат не записан. Для действий нужны бизнес-ключи идемпотентности либо проверка фактического результата перед повтором.
- Истёкший lease не останавливает уже начатый внешний эффект. Fencing защищает БД, а не произвольный внешний API.
- `paused` запрещает новую обработку workflow; факты сохраняются. При resume проверки и просроченные deadlines пересматриваются. Политику сдвига сроков автоматически не предполагаем.
- Отмена закрывает ожидающие и готовые задачи; для уже начатых действий отмена кооперативная и не отменяет совершённые эффекты.
- Hot reload может менять функцию проверки во время ожидания. Для MVP предлагаем явно документировать исполнение актуальной версии; закрепление версий и миграции ожиданий — отдельное решение до production.

## 7. Связь с существующим кодом

Hyper уже имеет Postgres-очередь на `agents`, run token, heartbeat, recovery и механизмы wake-up. Перед реализацией нужно проверить, какие из них можно расширить вместо дублирования. Существующие планы агента — пользовательское представление работы, не источник гарантий исполнения.

В `~/health-workspaces/libs/flow` полезны:

- function-based flow: `discover gaps → apply target → verify → receipt`;
- стабильная бизнес-идентичность gap и revision;
- обычные функции вместо отдельного языка;
- управляемое время для тестирования;
- атомарное завершение шага и создание продолжений в старом step runner.

Новый engine не обязан хранить gaps или превращать весь workflow в reconciliation-функцию. Агент может использовать такую функцию как один из инструментов принятия решений.

## 8. Минимальные проверки перед выпуском

1. Рестарт после регистрации ожидания и до освобождения агента.
2. Событие до регистрации, во время регистрации и после неё.
3. Одновременные событие и deadline; повторная доставка одного события.
4. Падение проверяющего worker-а и опоздавший результат после истечения lease.
5. Падение агента после внешнего действия, но до записи результата.
6. Атомарное завершение задачи с созданием следующего ожидания.
7. Два готовых задания одного агента без параллельного запуска координатора.
8. Ошибка функции, удалённая функция и изменение её версии.
9. Пауза, отмена и возобновление после прошедшего deadline.
10. Прогон недель ожидания с виртуальными часами без реального sleep.

## 9. Открытые решения

- Точное соответствие workflow и agent session: отдельная сессия на workflow, правила замены координатора.
- Повторное использование текущих wake/watch механизмов и их таблиц вместо новой `task_waits`.
- Lease задачи: привязать к run token агента или вводить отдельную попытку исполнения.
- Источники durable событий, курсоры и правила маршрутизации внешних сигналов.
- Политика версий функций и действия при несовместимом обновлении.
- Когда агент должен просыпаться из-за длительных ошибок проверок; лимиты частоты, бюджета и повторов.

Следующий шаг: согласовать минимальный API создания задачи с ожиданиями и получения готовых задач; затем сопоставить его с текущими `agent.wake*` и worker loop. Не начинать с нового scheduler-а, пока не проверено переиспользование существующего.
